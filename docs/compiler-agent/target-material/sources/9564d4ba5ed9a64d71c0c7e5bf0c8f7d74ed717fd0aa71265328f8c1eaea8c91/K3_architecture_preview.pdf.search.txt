SpacemiT K3: A RV A23 RISC-V AI CPU with 60 TOPS AI Compute
SpacemiT Preview Version.
Abstract
This paper presents SpacemiT’s second-generation edge CPU com-
pute subsystem, K3, which adopts a homogeneous fusion para-
digm: a high-performance RISC-V CPU cluster (X100) and an AI-
first RISC-V AI-CPU cluster (A100) are integrated under a unified
RISC-V ISA and run a single Linux operating system. K3 explores
how a compact, co-designed hardware–software stack can deliver
both general-purpose and AI capability within the constraints of
resource-limited edge hardware. The paper describes the engineer-
ing choices and implementation of the X100 and A100, with par-
ticular emphasis on RVA23 enablement and hardware–software
co-design for efficient LLM inference. It also outlines the OS sched-
uling and resource governance and AI software stack built on top
of K3, forming an integrated solution for edge AI and robotics.

1 Introduction
As edge computing moves into a new phase driven by local LLMs
and robotics, the key challenge is to deliver both strong general-
purpose performance and strong AI performance in a single system,
and to turn that into a scalable, cost-effective commercial product.
To address this, we propose and implement a homogeneous fusion
computing paradigm for the edge-AI era: under a unified RISC-V
ISA and extension framework, we integrate a high-performance
RISC-V CPU with an AI-optimized AI-CPU (or an ISA-integrated
AI compute unit). Both run the same operating system (Linux) and
support unified scheduling and resource governance with threads
or tasks as the basic scheduling units, thereby enabling a system-
level delivery model of “one platform, one stack, and one operations
surface. ”
This work corresponds to our second-generation silicon. In the
first generation, we validated the feasibility and customer value
of homogeneous fusion in real deployments: on the one hand, the
general-purpose RISC-V CPU ensures system and ecosystem com-
patibility, control-plane determinism, and engineering maintain-
ability; on the other hand, the ISA-integrated AI compute resources
can be invoked at low overhead within the same address space
and process model, substantially reducing system complexity and
ecosystem fragmentation for edge deployment. The evolutionary
path is analogous to the mobile Internet era: to achieve both high
performance and low power on smartphones, the industry intro-
duced big.LITTLE designs on top of the Arm ecosystem while
running a single operating system. In the AI era, our homogeneous
fusion targets both high performance and high AI throughput,
while compressing the system fragmentation cost introduced by
heterogeneity into a controllable range.

2 System Overview and Design Rationale
2.1 Design Targets and System Trade-offs
To deliver, based on the RISC-V architecture, a mass-production AI
CPU targeting two representative edge form factors—AI computers
and AI robots—we ultimately converge the engineering constraints
of the chip to the following three points:
• 12 nm process: adopt a 12 nm-class FinFET platform that
has entered long-term volume production and is explicitly
positioned for high-efficiency edge devices (e.g., 12FFC+ in
volume production; N12e targeting AI-enabled IoT/edge de-
vices), thereby reducing manufacturing and cost risk.
• Die area budget (<150 mm2): constrain die size to <150 mm2
to reduce per-die cost and yield risk (widely used industry
models indicate that die cost grows markedly super-linearly
with area and yield decreases as die area increases), and to
avoid dependence on supply-chain-constrained resources
such as oversized packages and high-layer-count substrates.
• 30 W power: set TDP to 30 W, consistent with mainstream
power envelopes of edge AI/robotics modules, enabling prac-
tical deployment within established thermal solutions and

It is important to emphasize that designing a mass-production-
grade edge AI CPU is fundamentally a software–hardware co-
designed system endeavor. Satisfying hard hardware constraints—such
as process node, area, and power—alone is insufficient to deliver
a product at scale. Practical deployability and commercial usabil-
ity are ultimately determined by the software stack, including the
compiler/operator libraries and runtime, OS and drivers, and the
toolchain for model deployment and performance analysis, as well
as their co-optimized convergence with the underlying microarchi-
tecture. Building on the software-stack assets and engineering vali-
dation accumulated from first-generation customer deployments,
we treat software generality and usability as the primary gating
constraint for the second-generation architecture design.

3 Hardware Design
In the K3 computing system, X100 and A100 achieve interoper-
ability under a unified RISC-V architectural framework; the im-
mediate value is manifested in the ability for general-purpose and
AI workloads to execute cooperatively within the same software
stack. More importantly, this approach avoids the coexistence of a
“dual-OS / dual-stack” configuration typical of conventional hetero-
geneous architectures, along with the resulting resource footprint,
boundary-crossing overhead, and maintenance complexity.

We observe that the AI software stack is continuously evolving
toward greater complexity and deeper reliance on open-source de-
pendencies: spanning kernels and device drivers, containers and
runtimes, compilers and frameworks, and the broader model ecosys-
tem, key capabilities are increasingly composed from a set of rapidly
evolving upstream open-source components. This trend makes it
difficult for a hardware vendor to sustain, over the long term, an
approach that “independently rebuilds a closed, proprietary stack”;
instead, system software must be able to track upstream community
iterations and upgrades over time in order to remain competitive in
functionality, performance, and security. In this context, adopting
Linux as the underlying operating system to host and integrate
these open-source components is the most natural and most sus-
tainable choice for constructing an AI software stack.
Within today’s mainstream RISC-V software ecosystem, the host
CPU domain typically uses Linux as the general-purpose software
substrate; meanwhile, in order to support AI frameworks and run-
times and to maintain long-term compatibility with upstream open-
source components, the device-side/accelerator-side AI software
stack is, from an execution unit perspective, also effectively com-
pelled to adopt Linux. If one follows the traditional heterogeneous
“host CPU + accelerator” design, this is essentially equivalent to run-
ning two largely identical Linux instances within the same system
(with substantial overlap in both the kernel and baseline user-space
components) and coordinating them via cross-boundary mecha-
nisms. Such duplicated stacks not only incur additional resource
consumption (memory, storage, and resident services), but also
introduce boundary-induced data-path and synchronization over-
heads (IPC, data copies, and context switches), and significantly
increase the complexity of version maintenance, security patching,
and the verification matrix—thereby undermining overall system
efficiency, maintainability, and long-term evolvability.
3.1 X100
X100 is a high-performance processor core based on the RISC-V
instruction set architecture, providing full compliance with the
RVA23 profile. It adopts a 4-wide dispatch, out-of-order microar-
chitecture, achieving high compute performance while balancing
energy efficiency and die-area cost. This design effectively targets
high-performance edge workloads and is also suitable for deploy-
ment in entry-level servers. To meet the requirements of high-
performance computing and scalable multicore integration, X100
incorporates key features including multicore interconnect, virtual-
ization support, reliability/ availability/ serviceability (RAS), and
security mechanisms.
From an architectural standpoint, X100 takes OpenC910 (the
open-source release of Xuantie C910) as the initial reference point,
and introduces extensive optimizations and functional enhance-
ments across multiple subsystems. The major improvements in-
clude: increasing frontend fetch bandwidth and improving branch
prediction accuracy; widening decode and dispatch and leveraging
multiple techniques to enhance execution efficiency; restructur-
ing the load/store subsystem to increase memory bandwidth while
substantially reducing access latency; adding a vector execution
unit compliant with the RISC-V Vector Extension v1.0; and refining
the multicore interconnect to improve scalability and coherence
support.
Beyond performance, X100 maintains a high degree of con-
formance and forward-compatibility in ISA support. For general-
purpose computing, X100 does not introduce any additional pro-
prietary ISA extensions, relying exclusively on the official RISC-V
standard instruction set. Building on this foundation, it tracks the
latest industry-standard evolution by supporting all mandatory
components of the RVA23 profile, while also implementing selected
optional extensions and additional extensions not explicitly enu-
merated in the profile, ensuring adaptability to future software-
ecosystem and hardware-platform evolution.
3.1.1 Frontend.
The increase in dispatch width of the X100 imposes greater demand
on instruction fetch bandwidth at the front-end. To address this,
the X100 processor core implements a series of key microarchitec-
tural optimizations aimed at significantly enhancing the effective
instruction fetch bandwidth. These enhancements ensure a sus-
tained and efficient supply of the instruction stream to the backend
execution units. The optimizations are primarily focused on two
critical dimensions: improving branch predictor performance and
increasing fetch parallelism.
Branch Target Prediction: The X100 incorporates targeted opti-
mizations to the timing path of the L0 Branch Target Buffer (BTB)
and moderately expands its entry capacity. Furthermore, by intro-
ducing a more sophisticated replacement algorithm better suited
to the locality characteristics of program branch accesses, the hit
rate of the L0 BTB is effectively improved. This enhancement di-
rectly reduces front-end bubbles and the associated fetch pipeline
disruptions caused by target address mispredictions.
Conditional Branch Direction Prediction: For conditional branch
direction prediction, the X100 employs a more advanced TAGE
(Tagged Geometric History Length) predictor, superseding the pre-
vious Bi-Mode algorithm. The TAGE predictor leverages long global
history patterns to make predictions, significantly improving the
prediction accuracy for complex control-flow behaviors.
Return Address Prediction: For function call returns, the X100
implements a Return Address Stack (RAS) based on a linked-list
structure. This design more robustly supports return address predic-
tion in out-of-order execution scenarios involving multithreading
or deeply nested function calls, thereby improving the prediction
performance for return instructions.
Instruction Fetch Bandwidth Optimization: To improve fetch
bandwidth, the X100 expands the organization of the Instruction
Cache (ICache) from 2-way to 4-way set-associative. This modifica-
tion effectively reduces the probability of cache misses due to way
conflicts, thereby enhancing the continuity of instruction supply. To
further mitigate access latency, the X100 increases the data transfer
bandwidth between the ICache and the L2 Cache from 128 bits to
256 bits per cycle. This reduces contention and occupancy of the
access channel to the lower-level cache.
Instruction Dispatch and Fusion: To fully leverage the backend’s
out-of-order execution capabilities, the X100 widens the instruction
dispatch bandwidth from three to four instructions per cycle. This
ensures that the decode and dispatch stages can continuously sup-
ply a sufficient stream of instructions to the backend. Additionally,

3.1.2 Midcore.
The mid-core encompasses the stages of instruction decode, rename,
dispatch, and issue. A primary focus of our microarchitectural re-
design at this stage was the transition from a 3-wide to an optimized
4-wide pipeline structure.
In the baseline OpenC910 architecture, the Instruction Decode
(ID) stage was 3-wide, while the subsequent Instruction Ready
(IR) stage had already been expanded to 4-wide to accommodate
potential instruction splits originating from the ID stage. To align
front-end throughput with backend capacity, we redesigned the
decode logic to support 4-way parallel decoding.
The increase in decode width necessitated corresponding en-
hancements in downstream pipeline structures to handle the higher
instruction throughput. We accordingly increased the depth of the
Issue Queue to accommodate a larger number of in-flight instruc-
tions, thereby preventing structural hazards caused by queue ca-
pacity limitations. Concurrently, we integrated an additional Arith-
metic Logic Unit (ALU) to mitigate structural conflicts arising from
insufficient execution resources.
The widening of the pipeline, deepening of buffers, and addition
of execution units invariably introduce deterministic timing chal-
lenges. To alleviate potential critical path degradation associated
with these expansions, we adopted a resource-sharing strategy for
the new ALU. Instead of adding dedicated register file read ports,
the new ALU reuses the read ports of the Branch Processing Unit
(BRU). Specifically, when no branch instruction is being issued, the
two integer issue queues can utilize the BRU’s register read ports
to dispatch instructions to the additional ALU. This port-sharing
approach enhances parallel execution capability while effectively
containing the growth of critical timing paths, mitigating the risk
of timing deterioration.
To further exploit the microarchitecture’s out-of-order execution
potential, we implemented several key optimizations within the
mid-core: 1. Immediate Operand Elimination: Logic was added to
eliminate the allocation of physical registers for certain immediate
operands, thereby alleviating register file pressure. 2. Early Wake-
Up: A strategy was adopted to release dependent resources early
during the execution of long-latency operations (e.g., division or L1

Its performance, typically measured by bandwidth and latency

The X100 incorporates two general-purpose pipelines, each equipped
with dedicated load/store units. Correspondingly, the data cache
(DCache) structure and organization were reconfigured to double its
access bandwidth. However, increased bandwidth often elevates the
out-of-order execution of memory instructions, potentially intro-
ducing more memory hazards—particularly false Read-After-Read
(RAR) and Read-After-Write (RAW) hazards—that incur substantial
pipeline flush and refill penalties. To mitigate this issue, the X100
implements a snoop monitor to filter false hazards and employs a
micro-operation (uop)-granularity hazard predictor. This predictor
proactively identifies potential data dependency conflicts and de-
lays the execution of conflicting instructions, thereby significantly
reducing latency penalties associated with memory hazards.
The X100 upgrades the bus width to 256 bits and utilizes a CHI-
like protocol to interface with the multi-core interconnect unit,
enhancing interconnection efficiency. Key optimizations include
restructuring several critical buffers:
• The Write Merge Buffer (WMB) was redesigned to improve
merging efficiency and bus utilization while maintaining the
same entry count.
• The Line Fill Buffer (LFB) and Victim Buffer (VB) were consol-
idated into a unified Fill & Victim Buffer (FVB). This resource-
sharing approach reduces total buffer resource overhead
while improving utilization efficiency, addressing structural
conflicts that previously limited outstanding request capac-
ity and thereby enhancing the core’s overall outstanding
transaction capability.
These buffer optimizations enable concurrent multi-line accesses
under the same cache index in both WMB and FVB, substantially
improving bus bandwidth utilization in data-intensive workloads
such as AI tensor operations.
The X100 implements several latency-focused optimizations:
• An early wake-up mechanism reduces load-to-use latency
in L1 miss/L2 hit scenarios.
• Atomic memory operations (AMOs) are executed more atom-
ically without instruction splitting, significantly lowering
AMO execution latency and reducing live-lock probability
during lock acquisition.
• The data prefetcher incorporates a Stream-based Page Prefetch-
ing (SPP) algorithm to improve coverage of irregular access
patterns, combined with a bus load feedback mechanism that
dynamically adjusts prefetch distance to balance timeliness
against bandwidth consumption.
The X100 adds support for the Hypervisor virtualization exten-
sion. To improve multi-level page table walk efficiency, it caches
intermediate page table entries in the TLB, effectively reducing
address translation overhead in virtualized environments. The de-
sign also implements ECC protection for the DCache and supports
handling Poison reporting from Data Check errors when supported
by the external bus interface, alongside compliance with the RISC-V
standard Reliability, Availability, and Serviceability Error Report-
ing Interface (RERI). These features provide essential support for
server-class applications.
3.1.4 Vector.
X100 integrates an efficient vector processing subsystem that de-
livers significant performance benefits for data-parallel workloads.
This subsystem is characterized by its full compliance with the
RISC-V Vector Extension Version 1.0 (RVV 1.0) and the RISC-V
Vector Crypto Extension to address the demands of data-intensive
computing and high-performance security applications.
Fundamentally, the X100 vector unit adheres to RVV1.0 with a
fixed vector length (VLEN) of 256 bits and maximum element length
(ELEN) of 64 bits, supporting data types from INT8 to INT64 and
FP16/BF16 to FP64. The architecture further enhances throughput
by featuring independent vector pipelines , including two arithmetic
pipelines and two load/store pipelines with each pipe dealing with
128-bit data, which can operate concurrently to maximize data
processing efficiency.
Decoupled Microarchitecture. At the microarchitectural level,
the X100 VPU employs a decoupled approach relative to the scalar
core. After initial decoding and scalar operand renaming within the
main pipeline, vector instructions are dispatched to an independent
vector unit for subsequent splitting and execution. Compared to the
tightly-interconnected modules of the scalar core, the vector unit is
functionally more separated and occupies a significant silicon area.
A decoupled vector unit not only provides enhanced flexibility and
configurability but also simplifies physical layout and floorplanning
for the core.
At the architectural level, the X100 vector employs a decou-
pled design strategy. After undergoing initial decoding and scalar
operand renaming in the main pipeline, vector instructions are
dispatched to a dedicated, independent vector unit for subsequent
issue,split and execution. This relative decoupled design is moti-
vated by the observation that the vector unit, compared to the
tightly-interconnected modules of the scalar core, is functionally
more separated and occupies a significant silicon area. A decoupled
vector unit not only provides enhanced flexibility and configura-
bility but also simplifies physical layout and floorplanning for the
core.
Vector instructions are first pushed in a dedicated vector instruc-
tion buffer, which serves to decouple them from the main pipeline.
Instructions are then issued from this buffer for further processing.
The vector unit supports the concurrent issue of up to two memory
instructions and two computational instructions. Each issue port
can handle an instruction micro-op in 128-bit granularity per cycle,
which means an instruction with LMUL=1 is issued as two 128-bit
micro-ops. The design choice of employing dual 128-bit data paths,
as opposed to a single 256-bit path, is primarily driven by the need
to balance hardware resource costs effectively. Given the wide va-
riety and high computational complexity of vector operations, a
finer-grained datapath width enables more efficient and balanced

main pipeline’s Load-Store Unit (LSU) for address calculation and
memory access initiation, while the data phase is handled by the
vector unit for operand splitting and vector register dependency
checking. Communication and data exchange between the two are
coordinated via instruction IDs. The LSU leverages its two existing
memory pipelines to issue and process two vector memory instruc-
tions in parallel. Correspondingly, the vector unit is equipped with
two matching splitter circuits to handle the data paths of these two
memory instructions. By decoupling address and data processing,
the main pipeline can forward instructions to the LSU as soon as
addresses are ready, without waiting for vector register dependen-
cies to be resolved. This allows the LSU to initiate memory accesses
promptly, thereby accelerating data retrieval and improving over-
all memory efficiency. Furthermore, for handling complex vector
memory patterns such as segment accesses, the LSU incorporates a
dedicated transpose buffer to accelerate data reorganization, signif-
icantly boosting execution efficiency.
3.1.5 Multi-core Interconnect.
The X100 architecture implements a systematic and comprehen-
sive upgrade to its multi-core interconnect system, targeting key
bottlenecks in high-performance computing and server workloads.
This upgrade achieves co-optimization across latency, bandwidth,
and overall system efficiency, spanning critical layers including the
cache hierarchy, memory subsystem, reliability mechanisms, and
coherence protocol.

The X100 transitions from an inclusive to an exclusive cache
policy. Furthermore, it introduces a superior cache tag backup mech-
anism for each core, enabling precise tracking of cache line states
across the multi-core environment. By eliminating redundant data
copies between cache levels, this approach effectively increases us-
able cache capacity. A 1:1.5 expansion ratio is employed to reduce
the frequency of back-invalidations. In terms of latency optimiza-
tion, the architecture enables early access to the L2 cache, with
pipeline operations canceled upon detected address conflicts. This
optimization significantly reduces the critical load-to-use latency,
as return data can be delivered directly to the core, bypassing the
additional latency introduced by access transaction queues. Follow-
ing these optimizations, the load-to-use latency for an L1 miss with
an L2 hit can be as low as 17 cycles, accelerating the resolution
of data dependencies. The prefetching mechanism has also been
enhanced. The memory subsystem integrates a next-line prefetcher
and a best-offset prefetcher. The former is trained on instruction
and page table walk (PTW) misses, while the latter is trained on
data access patterns. This combined approach improves both spa-
tial locality prediction and adaptability to complex access strides,
thereby boosting the overall cache hit rate.
The memory subsystem doubles the number of cache banks, sup-
porting parallel access to up to 4 banks. This significantly improves
memory-level parallelism and internal data bandwidth. To match
this design, the internal bus width has been expanded to 256 bits,
further unleashing the potential of memory bandwidth.
The multi-core coherence protocol benefits from several key op-
timizations. Bypass optimization techniques reduce the latency of
common snoop transactions by 4 cycles. The architecture supports
self-snooping, effectively resolving cache aliasing issues within
a core, and enables precise bank snooping to reduce power con-
sumption. The internal state machine of the transaction queue
has been redesigned, shortening the lifecycle of common multi-
core transactions and improving overall interconnect efficiency.
For high-concurrency lock acquisition scenarios, an exclusive Clea-
nUnique transaction type has been introduced. This strategically
avoids live-lock issues under heavy load, enhancing system stability
in highly competitive environments.
For server-grade Reliability, Availability, and Serviceability (RAS),
the X100 introduces a standard error reporting mechanism compli-
ant with the RISC-V RERI specification. This is integrated with the
foundational software layer to enable more accurate error handling
and system recovery. Regarding data integrity, the architecture
implements a poison mechanism for error tagging and propagation.
This is combined with data check technology to detect bus trans-
mission errors. The system can flexibly choose between delayed
reporting of error information via the RERI interface or immediate
return of traditional error signals. This flexibility allows the sys-
tem to balance reliability requirements with real-time performance
constraints.

3.2.1 Vector.
The A100 Vector Unit is driven by two parallel vector pipelines
that perform vector-instruction splitting, dependency handling, and
vector register-file reads/writes, with results produced primarily
in stages VE3–VE5. From an execution-organization perspective,
the Vector Unit classifies operators into five categories according
to "instruction types + datapath characteristics”: INT, FP, CRYPTO,
FDV, and IME-1.0.
The register file is provisioned with VLEN = 1024-bit vector reg-
isters, comprising 32 architectural vector registers (v0–v31). This
register width determines that a single vector instruction can oper-
ate on up to 1024 bits of data per instruction instance, substantially
increasing achievable throughput.
Compute-resource provisioning follows a simple guiding policy.
High-frequency, throughput-critical operators (add/sub, compare,
shift, logic, and narrow-width multiply–accumulate) are preferen-
tially mapped to wider execution resources capable of dual-issue,
and are scheduled to produce results as early as possible in VE3
(or VE4). Mixed execution widths follow the principle of “fixing
width by mainstream precisions, slicing/packing by precision, and
reusing resources for rare widths”: mainstream data types such
as INT8/INT16/BF16 define the critical datapath widths and lane
counts; lane slicing and element packing increase parallelism for
narrow precisions; and the relatively infrequent wider datapaths are
realized via cross-lane merging or multi-cycle time-multiplexing to
avoid over-provisioning for peak width. Low-frequency or struc-
turally complex operators (e.g., permute/reorder, partial wide-width
datapaths, and iterative division) deliberately constrain issue band-
width and datapath width to improve area and energy efficiency.

3.2.3 Memory Subsystem.
A100’s memory-system optimizations concentrate on two access
paths: local memory and main memory. When viewed across dif-
ferent phases of LLM computation, the former primarily serves the
compute-bound phases characterized by high arithmetic intensity
and strong data reuse (i.e., the core vector/matrix operators), with
the objective of keeping the working set resident in near-core stor-
age as much as possible to provide stable data supply and minimize
stalls. The latter primarily covers more memory-bound stages such
as parameter reads and cache updates (especially the streaming
access pattern during decode), with the goal of delivering robust
sustained read bandwidth from the main-memory subsystem while
providing sufficient latency-hiding capability.
The capacity provisioning of local memory is typically not the
result of optimizing a single metric to its extreme; rather, it emerges
from a multi-objective trade-off between performance benefit and
implementation cost under the target system goals, where cost
includes, but is not limited to, area, power, and bandwidth over-
head. This configuration is also materially constrained by physical-
implementation factors, such as frequency ceilings imposed by
timing closure and area boundaries dictated by macro placement
and interconnect routing. Accordingly, this design choice can be for-
malized as a canonical Pareto-optimal multi-objective optimization
problem: selecting, within the feasible design space, a compromise

3.3 Support for New RISC-V Features in K3
During the iterative evolution of our company’s chip products, the

3.3.1 Hypervisor.
Virtualization abstracts physical hardware resources such that mul-
tiple virtual machines (VMs) can execute concurrently on a single
physical platform, thereby significantly improving resource utiliza-
tion, strengthening isolation, and enabling flexible multi-tenant
deployments. In the RISC-V ecosystem, virtualization is enabled via
the Hypervisor extension (H-extension), which provides efficient
hardware support for both CPU and memory virtualization. In ad-
dition, the Advanced Interrupt Architecture (AIA) introduces the
IMSIC, enabling CPU cores to receive MSI interrupts and to deliver
interrupts directly to guest VMs, substantially reducing interrupt-
handling overhead and latency in virtualized environments.
On the K3 platform, the X100 core implements the Hypervisor
extension, and each physical core can support up to seven active
VMs. However, the two-stage address translation required by vir-
tualization introduces additional translation overhead, which can
materially impact application performance inside VMs. To miti-
gate this performance loss, the X100 core incorporates multiple
optimizations at the translation lookaside buffer (TLB) level. First,
the instruction TLB (ITLB) and data TLB (DTLB) directly cache
translations from guest virtual addresses (GVA) to system phys-
ical addresses (SPA), such that, on an L1 TLB hit, virtualization
incurs no additional translation latency. Second, the L2 TLB not
only retains GVA→SPA mappings, but also caches guest physi-
cal address (GPA) to SPA mappings to expand address-translation
coverage. Furthermore, the page-table-walker (PTW) caches store
non-leaf page-table entries for GVA→GPA translation, accelerating
page-table walks upon guest TLB misses. Collectively, these mech-
anisms aim to reduce memory-access latency and improve overall
execution efficiency under virtualization. After enabling the above
virtualization support, detailed performance comparisons for the
X100 core are reported in Section 6.1 of this paper.
With respect to interrupt support, both the X100 core and the
A100 core in the K3 platform support receiving external interrupts
in the form of MSI. Specifically, on X100, both machine mode (M-
mode) and supervisor mode (S-mode) support MSI external inter-
rupt IDs 1–511; in addition, enabled by the Hypervisor extension,
each VM running in virtual supervisor mode (VS-mode) can support
direct MSI passthrough for interrupt IDs 1–63. For A100, M-mode
and S-mode likewise support MSI external interrupt IDs 1–511;
however, because this core does not implement the Hypervisor
extension, it cannot provide VM-oriented interrupt passthrough.

3.3.2 Vector Crypto.
Cryptographic operations are fundamental for data security and
communication privacy. However, scalar ISAs often face throughput
and energy-efficiency bottlenecks for large-scale or high-throughput
crypto workloads. To address this, RISC-V introduces Vector Cryp-
tography extensions, providing vector-oriented crypto instructions
that significantly improve parallelism and execution efficiency.
The extension covers both international-standard algorithms
(e.g., AES, SHA-2) and Chinese commercial cryptography algo-
rithms (e.g., SM4, SM3). By operating on structured vector element
groups (Element Groups), it efficiently supports encryption/decryption,
key expansion, and hashing. Its ISA design emphasizes data-independent
execution latency, improving resistance to timing side-channel at-
tacks. It also supports multiple configuration “suites” (e.g., Zvkn,
Zvks), balancing flexibility with specialized hardware optimization.
In K3, both X100 and A100 implement Vector Crypto modules.
They share the same implementation policy: SM3 and SHA2-64
use 256-bit element groups, while all remaining instructions use
128-bit element groups. With Vector Crypto enabled, typical en-
cryption/decryption kernels can achieve up to 60×performance
improvement over scalar execution; detailed data are reported in
Section 6.1.
3.3.3 Precision Conversion Extensions.
To meet the growing demand for large-model training and infer-
ence, efficient low-precision compute has become critical. Both
X100 and A100 are fully compatible with the RVA23 optional exten-
sion subsets for half-precision floating-point compute, including
Zfh, Zvfh for FP16 scalar/vector operations, and Zfbfmin, Zvfbfmin,
Zvfbfwma for BF16 and BF16 matrix operations. This unified ISA
support ensures software compatibility and portability for foun-
dational FP16/BF16 operations, providing essential low-precision
compute capability for AI workloads.
Notably, A100 further integrates customized vector conversion
instructions for FP8, supporting both E4M3 and E5M2 formats.
FP8, as an emerging lower-precision format, can halve storage
and transfer costs while maintaining acceptable numerical stability
for key applications. Through tight microarchitectural integration,
A100 implements these conversions into the execution pipeline,
substantially reducing FP8 to FP16/BF16 conversion latency and
improving conversion efficiency by orders of magnitude.
At the time of K3 design, RISC-V did not have an official OFP8
extension; as of this writing, RISC-V is defining a corresponding
OFP8 standard. Once ratified, future cores will migrate to the official
standardized extension.
Hardware-level precision conversion provides benefits beyond
conversion speed. Modern AI models widely adopt mixed-precision
strategies, since different layers/ops have different numerical sen-
sitivity and may employ different quantization methods. A100’s
precision-conversion instructions enable dynamic, efficient on-
demand precision switching across phases or compute units, greatly
reducing the high overhead of software-emulated conversions.
Because data can be stored at higher precision only when nec-
essary—and otherwise converted at low cost—this effectively re-
duces off-chip bandwidth demand, which is crucial for bandwidth-
bottlenecked AI acceleration scenarios.

4.1 Operating System
From a hardware-architecture perspective, although the X100 and
A100 processors share a homogeneous core lineage, their functional
roles differ substantially, forming a typical asymmetric compute ar-
chitecture. X100 prioritizes general-purpose compute performance,
whereas A100 is optimized specifically for AI and high-throughput
vector computation. This specialization is reflected in both the
ISA feature set and hardware configuration: X100 implements the
Hypervisor extension and is suitable for general server scenarios
requiring hardware-assisted virtualization; its vector length (VLEN)
is 256 bits, targeting general-purpose vector processing. In contrast,
A100 does not implement the Hypervisor extension, but increases
VLEN to 1024 bits, enabling a significant throughput advantage for
large-scale matrix operations and tensor computing.
Such asymmetry introduces challenges to OS-kernel schedul-
ing. To exploit the flexibility of the fused heterogeneous platform
while preserving deterministic execution behavior, we design and
implement a core-affinity-based scheduling scheme. In the current
system, all 16 cores across X100 and A100 are managed by the Linux
kernel as an SMP system, and the OS exposes a unified 16-core log-
ical view. However, the scheduling policy is explicitly partitioned:
the 8 A100 cores are designated as AI-dedicated accelerator cores,
serving only specific AI algorithms and vector-compute-intensive
tasks, and are excluded from general-purpose workload handling.
Accordingly, user threads are, by default, bound to the X100 core set
at creation time. Even when the X100 set is saturated, the system
does not migrate these workloads onto A100. Conversely, when a
task (e.g., AI inference or algorithms optimized to leverage 1024-bit
vectors) requires A100, the application must bind the correspond-
ing threads to the A100 core set after thread creation. Once bound,
these threads are constrained to execute only on A100 for their
entire lifetime and are prohibited from migrating to X100.
While this policy addresses the baseline issues of mixed sched-
uling between X100 and A100—ensuring ISA compatibility (e.g.,
preventing a thread composed only of general instructions from
being incorrectly scheduled onto an A100 core that supports only
a subset of AI-related instructions, which could otherwise trig-
ger exceptions)—it also introduces system- and engineering-level
complexity. First, from a load-balancing perspective, the policy is
not optimal: it may leave the A100 set idle while the X100 set re-
mains fully utilized, reducing overall resource utilization. Second,
cross-core migration is constrained by the need to strictly avoid
scheduling mismatched vector contexts (e.g., different VLEN state)
across core types, increasing scheduler complexity. Third, from
a software-ecosystem standpoint, the current approach relies on
modifying Linux kernel code, which is unfavorable for long-term
maintenance and difficult to upstream into the mainline kernel
community. In addition, application developers must understand
the underlying hardware-aware scheduling behavior to optimize
effectively, raising the development barrier.
To address these challenges, we are exploring an improved ap-
proach based on the Linux cpuset mechanism. This approach im-
plements disciplined scheduling management by partitioning pro-
cessor affinity domains: X100 cores (CPU0–7) are configured as the
default domain, while A100 cores (CPU8–15) are configured as an
13
SpacemiT, Preview Version, 2026/01/29
AI-exclusive domain. System workloads run in the default domain
by default. Only when a task is explicitly labeled by the application
as an AI task is it allowed to be placed into the AI-exclusive domain.
This method shifts policy enforcement from kernel modifications
to user-space configuration, leveraging Linux’s native resource
isolation and management framework, and is expected to provide
clearer and more sustainable heterogeneous scheduling support
while reducing overall system complexity.
4.2 AI Algorithms and Software Stack
An AI-DSA processor core that implements a complete set of RVV
and tensor-extension ISAs runs on top of Linux. It exploits multi-
thread scheduling to express the parallel, tile-based computation
pattern in AI inference, while the general-purpose X100 cores regu-
late load balancing across A100 cores and provide fast-response syn-
chronization, and can also handle selected asynchronous memory-
transaction tasks. On this foundation, we build an AI compute
software stack that integrates a hand-tuned operator library, an
AI compiler, and a runtime system. The stack follows a pragmatic
evolution path: first achieve peak performance for proprietary sce-

4.2.1 - End-to-end deployment form factor and engineering imple-
mentation highlights.
Unified API operator library. At the outset of AI software devel-
opment, we commit to two parallel tracks: a hand-written-kernel
inference engine and an AI compiler. The operator-library APIs
are aligned with MLIR meta-op definitions, which ensures seman-
tic completeness and cross-framework compatibility. At the same
time, it exposes a C API that early versions of the AI compiler can
invoke. This allows the full compilation pipeline to be exercised
before complete IR-based code generation is in place, which is a key
enabler for K3 to bring up both AI inference and AI compilation
rapidly in the early post-silicon phase.
X100 runtime system. Both the AI-compiler path and the inference-
engine path rely on X100 to schedule AI workloads onto the two
A100 clusters. In the inference abstraction, all operators—such as
convolution and GEMM, as well as Triton-compiled kernels—use an
A100 cluster as the hardware scheduling unit, which maps equiva-
lently to a group of four A100 Linux threads. With two A100 clusters,
the system forms two groups totaling eight A100 Linux threads,
conceptually analogous to CUDA multi-stream execution. The X100
runtime dynamically dispatches tile-level compute tasks issued by
the inference engine and by Triton onto the currently least-loaded
A100-cluster thread group. In subsequent designs, K3 will further
support distributed inference, where the runtime becomes topology-
aware and schedules tile tasks in a locally optimal manner, thereby
preserving a transparent programming model while improving the
scalability of the inference engine.

5.1.2 Virtualization Performance.
For virtualization performance evaluation, we use the same hard-
ware configuration (X100 cores at 2.4 GHz with LPDDR5-6400) and
quantify general-purpose compute performance under virtualiza-
tion using the SPEC CPU2006 integer suite (CINT2006). The results
show that the virtualization overhead varies significantly across
benchmarks due to differences in computational characteristics,
with performance losses ranging from 0.1% to 16%. Overall, virtual-
ization reduces the aggregate SPEC CINT2006 score by 5.48%, as
summarized in Table 5.
A closer examination of per-benchmark results indicates that the
performance loss correlates strongly with the workload’s memory-
access behavior and control-flow complexity. Benchmarks with
irregular memory-access patterns that limit the effectiveness of
hardware prefetching (e.g., 429.mcf), as well as benchmarks with
complex control flow and hard-to-predict branches (e.g., 403.gcc),
exhibit more pronounced slowdowns under virtualization. The un-
derlying cause is the increased penalty on TLB misses due to the
additional address-translation stage introduced by virtualization
(e.g., two-stage translation via mechanisms such as EPT or shadow
page tables). When a workload’s access stream cannot be effectively
covered by the TLB, each translation miss triggers an extra map-
ping step from guest-physical to host-physical addresses, which
increases effective memory-access latency and intensifies pressure
on the memory subsystem, thereby further degrading performance.

5.2 AI Performance
5.2.1 Memory Read Bandwidth.
For LLM inference, decode-phase TPS is often dominated by effec-
tive read bandwidth: generating each token triggers a full-model
forward pass, and if weights/intermediate data cannot remain resi-
dent in cache over time, the bottleneck shifts from compute to the
sustained throughput of reading data from memory.
A memory-access pattern that more closely matches the hard-
ware objective of “fully utilizing the memory controllers” is thread-
sharded multi-stream sequential read. In this pattern, a contiguous
physical address range (or a page/block-partitioned region) is di-
vided into N non-overlapping streams (chunks); N threads/cores are
pinned, and each core linearly scans its own stream with cacheline
strides (optionally assisted by prefetching). The streams run in par-
allel with minimal barrier synchronization, continuously issuing
read requests so that the memory controllers can saturate the read

5.2.2 Advantages of 1024-bit Vectors.
With RVV configured at VLEN=1024 and 32 architectural vector
registers, the programming model can be viewed as providing an
effective 4 KB ultra-fast local scratchpad, which enables stronger
locality optimizations in certain specialized scenarios.
Norm-style broadcast computation. This pattern typically takes
the form C = A[..., C] * Scale[C], where the channel dimension C
is often 128/256/512/768. With VLEN=1024, 16 vector registers are
sufficient to hold the Scale vector for C < 512, so the Scale tensor
only needs to be loaded once globally. This reduces pressure on the
L1/L2 caches by avoiding repeated scale fetches during the main
compute loop.
FlashAttention. In FlashAttention, the hidden dimension is com-
monly 128 or 64. Under FP16 precision, two vector registers can
hold the hidden dimension for one sequence chunk. Even without
tensor-extension instructions, RVV alone can eliminate the inner
loop over the hidden dimension, and keep the𝑉·𝑄𝐾 accumulation
resident in 2-4 vector registers, making the compute path largely
independent of L1/L2 caching during the accumulation phase.
Reducing the likelihood of VPR spills. During compiler register
allocation, code that heavily uses LMUL=4 or LMUL=8—especially
in transcendental-function approximations such as exp and tanh—is
prone to vector register spills, which degrades the instruction sched-
ule and overall performance. With VLEN=1024, using LMUL=1 can
provide a compute width equivalent to VLEN=256 with LMUL=4,
substantially reducing the probability of vector-register spills and
improving kernel robustness.
