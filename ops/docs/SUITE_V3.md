# Development corpus v3: the declared inference subset

v3 replaces the target-independent v2 suite with a **declared subset for LLM
inference**. The definition of the subset — five principles, included
constructs, excluded constructs — is [`SUBSET.md`](SUBSET.md). This document
is the selection record: method, before/after numbers, coverage, the
dev/perf/held-out split, validation status and the differences from v2.

## 0. At a glance

| | v2 (`SUITE_V2.md`) | v3 |
|---|---:|---:|
| universe audited | 1659 candidates | **1600** operators (`basic` 48, `medium` 47, `hard` 155, `bench` 100, hidden 1250) |
| declared subset / pool | — | **1000** operators, 5612 cases |
| workflow input | 500 operators, 2893 cases | **500** operators, **2734** cases |
| dev (correctness) | 400 / 1717 | **400 / 2192** |
| perf (performance) | 100 / 1176 | **100 / 542** |
| held-out | 1088 hidden | **500 / 2878** (pool minus suite) |
| compile identities (meta) | 1422 | **2161** (1.26 cases/identity) |
| features covered | 76 / 76 | **75 / 75** of the declared subset |
| interactions covered | 1649 / 1663 | **1612 / 1612** of the declared subset |
| backward operators | 64 in the suite | **0** (principle 1) |
| validated on stock Triton 3.8 | 2850 / 2850 | **pool 5612 / 5612, suite 2734 / 2734, held-out 2878 / 2878** |

The feature count is one lower than v2 because `dot.precision_kw` no longer
exists in the subset: tf32/tf32x3 and the `input_precision=`/`allow_tf32=`
arguments were stripped from every kept operator (principle 2). That is the
closure rule, not a regression: the language the compiler is asked to
implement got smaller by exactly one construct.

## 1. Method

The pipeline is three deterministic steps; every script is in `harness/tools/` (maintenance branch only)
and rerunnable.

1. **Universe audit** (`build_v3_pool.py plan`). AST feature extraction
   (`harness/opslib/features.py`, no execution, no name matching except for
   the family classifier), family classification, near-duplicate hashing.
2. **Apply the five principles** to the universe, producing the pool:
   - principle 1: remove 106 backward operators;
   - principle 2: remove 46 libdevice operators + 7 float64-case operators;
     strip `input_precision=`/`allow_tf32=` and the knobs feeding them from
     the 68 surviving files (of 127 upstream files);
   - principle 3: remove 1 operator that calls `tl.tanh` (absent in Triton
     3.8) and declare the API from what remains;
   - principle 4: keep every `@triton.autotune` operator (21 in the pool);
   - principle 5: collapse **224 exact structural duplicates** and **164
     redundant variants** of over-represented skeletons to representatives,
     plus **52 operators with no semantic-size correctness case** (their case
     layer hard-codes a performance-size axis, or `SHAPES` is not a tensor
     shape). Never by line count. All 82 forward linear-attention and 16
     attention kernels are protected, and the pool keeps every feature and
     interaction of the forward+portable universe.
   The pool is **1000 operators / 4030 cases** before case enrichment
   (§10); after the inference-dtype enrichment it is **1000 / 5612**.
   `removed.json` lists all 600 removals with the principle and, for
   representatives, the kept operator it duplicates.
3. **Select the workflow input** (`build_suite_v3.py`):
   - **perf 100** = the 96 surviving `bench/` operators (they already carry
     steady-state workload rules) + 4 forward analogues replacing the bench
     operators the subset excludes (table in §5);
   - **dev 400** = `select_suite.select` (the v2 selector, reused unchanged)
     from the remaining 900 pool operators, seeded with the perf lane:
     stage 1 cheap weighted set cover over features + interactions, stage 2
     diversity under a per-tag-set cap (3), stage 3 farthest-point fill.
     A family floor of 4 dev representatives is applied with a
     coverage-preserving swap. `docs/COVERAGE_MATRIX.md` is generated by the
     same call.
   - **held-out 500** = pool minus suite, recorded by origin in
     `suite/heldout.json`; it never enters the repository operator dirs.

Materialisation to the pool (outside git) and to `suite/`:

- `tl.dot` precision knobs stripped (`v3_transforms.strip_dot_precision`);
- `SHAPES` normalised to semantic sizes: an axis above 128 becomes the
  largest divisor of itself in `[64,128]` when one exists (so `% BLOCK == 0`
  arithmetic survives), otherwise `96 + dim % 32` (so non-divisible tails
  survive); at most 4 shapes per operator. 18 operators use a verified
  override (their shapes are keyed configs or must be a power of two); they
  are listed in the pool work directory. Task 2 (§10) then applies a
  representative shape rule on top of this list.
- case enrichment (§10): every floating operator that stock Triton can run in
  low precision declares `float32` / `float16` / `bfloat16`; the representative
  shape rule keeps the typical shape, one tail shape and one degenerate shape,
  and drops redundant aligned shapes first. Cases whose new dtype/shape does
  not pass stock Triton are dropped for that operator and listed in §10.
- `suite/dev/provenance.json` and `suite/perf/provenance.json` record the
  origin path, pool path and sha256 of every suite file.

The task's starting table (elementwise/reduce 568, matmul 469, norm 194,

  `cumsum` / `cumprod` families — all of them, no line-count filtering.
- **16 attention** operators (flash / decode / paged / varlen).
- **98/98 protected** inference kernels (linear attention + attention).
- **75/75 features and 1612/1612 interactions** of the forward+portable
  universe. The only universe feature that does not survive is
  `dot.precision_kw`, removed on purpose by principle 2.

Reading the table:

- v2's 1649 interactions are not a superset of v3's 1612: v2 also counted
  `dot.precision_kw` interactions and its suite contained 64 backward
  kernels. v3 optimises coverage of a **smaller declared language** and
  reaches 100% of it with 500 operators.
- The dev lane alone covers 1609/1612 interactions; the remaining 3 are
  covered by the perf lane (bench kernels with distinctive fused epilogues).
- The held-out set is deliberately *not* coverage-saturated (70/75 features,
  1175/1612 interactions): it is the generalization probe, not a second dev
  set. It contains 112 matmul variants, 123 norm and 50 linear-attention
  operators that the suite does not show the compiler.

## 4. Validation

Every operator is run on **stock Triton 3.8** against its NumPy `ref` with the
corpus runner, `TRITON_F32_DEFAULT=ieee`, on GPUs 4 and 5. One subprocess per
operator: a single illegal memory access poisons a CUDA context, and the
runner then reports every later case in the same process as `LAUNCH_FAIL`
(the first naive pool run had 1370 such cascade rows). Stock Triton's
autotuner imports torch for `do_bench`, so validation passes `--allow-torch`;
operator files themselves never import torch.

| run | operators | cases | result |
|---|---:|---:|---|
| pool (final) | 1000 | 5612 | **5612 / 5612 PASS** |
| suite (dev+perf) | 500 | 2734 | **2734 / 2734 PASS** |
| held-out (pool minus suite) | 500 | 2878 | **2878 / 2878 PASS** |

During construction, 52 operators were removed because no semantic-size case
passes (case-layer performance-size axis or non-tensor `SHAPES`); each is in
`removed.json` with the failing case and status. Nothing was fixed by
loosening a tolerance, editing a `ref`, or deleting a passing case. The 18
shape overrides only *narrow* `SHAPES` to the upstream-declared shapes that
pass (or to a power-of-two semantic size); they never change `ref`.

## 5. The performance lane

`suite/perf` is 96 `bench/` operators + 4 forward analogues. The four bench
operators excluded by the subset and their replacements:

| excluded | principle | replacement | why it is the analogue |
|---|---|---|---|
| `bench/index_select_bwd` | 1 (backward) | `basic/gather_1d` | forward gather |
| `bench/l2_norm_bwd` | 1 (backward) | `medium/l2_norm_triton1` | forward row L2 norm |
| `bench/swiglu_backward` | 1 (backward) | `medium/swiglu_fwd` | forward SwiGLU |
| `bench/tanh` | 3 (`tl.tanh` absent) | `hidden/tanh` | tanh via `1 - 2/(exp(2x)+1)` |

`suite/perf/workload.json` keeps the 96 original steady-state rules and clones
the class / pattern / scale rule / bytes model of each removed entry for its
replacement, so class balance (memory / reduction / compute) is unchanged.
After case enrichment (§10) each operator is timed once per **declared**
floating dtype: 239 entries cover the 100 perf operators — 74 declare
`bfloat16` (primary), `float32` and `float16` (9 of those (operator, dtype)
timing entries are dropped, see §10.6), 25 only in `float32` because
their kernel calls a Triton math intrinsic that accepts fp32/fp64 only, and 1
integer operator keeps `int32`. Correctness shapes in `suite/perf` are semantic
sizes; the steady-state sizes used for timing are resolved from
`workload.json` by `harness/benchmark/size.py`.

## 6. dev / perf / held-out protocol

- **dev** = `suite/dev` (400 operators, 2192 cases). The compiler may look at
  these.
- **perf** = `suite/perf` (100 operators, 542 cases). Correctness gate + steady-state
  timing; the performance lane is not part of the correctness gate budget in
  the v2 sense (it has its own workload rules).
- **held-out** = `suite/heldout.json` (500 operators, 2878 cases), recorded
  by origin. Sample it **stratified by family and feature interaction**, not
  randomly: 112 of the 500 are matmul variants, 123 norm, 50 linear
  attention; random sampling over-represents the elementwise majority and
  over-estimates generalization.
- Evaluation metrics: compile success rate, correctness rate, failure rate
  bucketed by feature/interaction, and failure rate on interactions never
  seen in dev.
- **Do not** merge held-out content into `suite/`; `suite/heldout.json` and
  `suite/manifest.json`'s `origin` field are the exclusion list.

## 7. Compile economics

Measured with `python3 harness/compiler_api/run_cases.py --dry-run
--group-order --identities`:

| tier | identities | cases | cases/identity | reuse |
|---|---:|---:|---:|---:|
| dtype | 1318 | 2734 | 2.07 | 51.8% |
| triton | 1927 | 2734 | 1.42 | 29.5% |
| **meta** (target) | **2161** | **2734** | **1.26** | **21.0%** |
| structural | 2001 | 2734 | 1.37 | 26.8% |

The enriched v3 is larger than the first v3 pass (2161 identities / 2734 cases
vs 1033 / 1545) because three inference dtypes are now exercised, but it is
still much smaller than v2 (1422 / 2893) in compile work. At the v2-measured
0.36 s/identity for stock Triton 3.8, one stock-Triton pass over v3 is ≈13 min
single-threaded, 1–2 min at 16-way concurrency.

## 8. Differences from v2, in one list

1. **Forward-only**: 64 backward operators left the suite (106 from the
   universe). v3 is the first suite that contains no gradient kernel.
2. **No vendor numerics**: tf32/tf32x3 knobs stripped from 68 pool operators;
   fp8 declared excluded (no upstream operator used it); libdevice and
   float64-case operators removed.
3. **Shape rule enforced**: all suite cases are semantic-size; performance
   sizes live only in `workload.json`. 52 operators whose case layer
   hard-coded performance sizes were removed (each with its failure).
4. **Representatives, not counts**: 224 exact duplicates + 164 redundant
   variants collapsed; the pool is 1000 instead of 1600 while keeping 100%
   of the declared language's features/interactions.
5. **Perf lane repaired**: 4 excluded bench operators replaced by forward
   analogues, class balance preserved.
6. **New held-out set**: 500 pool operators by origin (`suite/heldout.json`),
   not the 1088 hidden operators v2 used (many of which were backward or
   perf-size-only and cannot be judged against the v3 language).
7. The suite manifest now records `family`, `origin`, and whether dot
   precision was stripped for every operator; provenance files record origin,
   pool path and sha256.

## 9. Limits

1. Family classification is heuristic (names + AST); the two totals (universe
   1600, pool 1000) are exact, the per-family rows are a taxonomy.
2. Features/interactions are AST approximations; 76/75 and 1664/1612 are
   *language samples*, not specifications.
3. 52 deep-GEMM scheduling variants left the pool because their case layers
   cannot produce semantic-size cases; their skeleton remains represented.
4. The held-out set is from the same pool, so it measures generalization
   inside the declared subset — by design. It says nothing about fp8, tf32,
   training, or TMA.

## 10. Task 2: inference dtypes and representative shapes

Task 1 fixed *which* operators are in the pool and the suite. Task 2 changed
only the **case layer** (`SHAPES` / `DTYPES` / `make_case`), the shared
tolerance table and the generated records. No operator was added to or removed
from the pool, suite or held-out set.

### 10.1 Method

- **Dtypes.** Every floating operator whose case layer is dtype-generic
  declares `float32`, `float16` and `bfloat16`. Integer / index operators keep
  their integer dtypes; `int8` remains on the quantised paths, and
  `int32` / `int64` remain on index-width-sensitive operators. Operators whose
  semantics is tied to one dtype keep it: `bitcast` (32-bit reinterpretation),
  bool masks, integer counters and the `median_*` key encodings. Operators
  that call a Triton math intrinsic which stock Triton only implements for
  fp32/fp64 (`tl.exp`, `tl.log`, `tl.sqrt`, `tl.erf`, `tl.sin`, `tl.cos`,
  `tl.sigmoid`, ...) keep `float32`; the operator would have to cast inside
  the kernel to do otherwise, and this task does not edit kernels.
- **Case builder.** `harness/tools/enrich_cases.py` appends a per-file
  `make_case` wrapper. It builds one base case, temporarily routes the
  module's `ref` through `case_utils.convert_float_arrays` so the expected
  values are computed from the *low-precision inputs*, and re-expresses the
  buffers through `case_utils.dtype_case`. `pointer_dtypes` is set for bf16
  (host float32 values already rounded to bf16), in-place aliasing is
  preserved, and integer/bool outputs stay bit-exact.
- **Shapes.** The representative rule keeps the typical shape, one tail shape
  (some axis > 1 not a multiple of 16) and one degenerate shape (an axis of
  1). Redundant aligned shapes are dropped first. A shape that is an
  operator's *only* tail or *only* degenerate shape is never dropped. For
  single-shape dev operators with no tail, one tail variant is added; if it
  does not pass stock Triton it is removed and recorded. Held-out uses the
  same rule but gets no added shapes.
- **Perf lane.** `bfloat16` is the primary declared dtype. The workload is
  expanded so each perf operator is timed in every declared floating dtype at
  the same steady-state rule (`suite/perf/workload.json`, 239 entries for 100
  operators; §10.6 lists the 9 dropped entries).
- **Tolerances.** One table in `harness/opslib/case.py`, derived only from the
  case dtype. No operator supplies its own tolerance on an enriched case.
  Exact and semantic comparators (`array_equal`, `quantized_interval`,
  `allclose_sign_invariant`) are preserved because they are not tolerances.
- **Fixes required by the review.** The last `linalg.dot.allow_tf32` tags and
  the `ALLOW_TF32=True` prose were removed from the 3 suite files and 10 pool
  copies (no `allow_tf32` / `input_precision` token remains in an operator
  file). The stale `tl.dot 默认 TF32` comment was rewritten to IEEE. In
  `suite/perf/det.py` the case inputs are now a well-conditioned
  `I + 0.001*N` matrix with an exactly-1 diagonal, so `det` stays finite at the
  benchmark size (n=256) and the check is no longer vacuous; `ref` still
  computes the determinant and was not changed.

### 10.4 Tolerance table

The table is in `harness/opslib/case.py` (`DTYPE_TOLERANCES`) and is applied
uniformly by `case_utils.comparison_for` / `dtype_case` to the dtypes the
enrichment adds:

| case dtype | rtol | atol | comparator | why |
|---|---:|---:|---|---|
| float32 | 1e-3 | 1e-3 | `allclose` | only where fp32 is a newly added dtype (the operator had no fp32 case before) |
| float16 | 1e-2 | 1e-2 | `allclose` | 10-bit significand, fp32 accumulation |
| bfloat16 | 2e-2 | 2e-2 | `allclose` | 8-bit significand; wider exponent but coarser mantissa than fp16 |
| integer / bool output | exact | exact | `array_equal` | integer arithmetic and masks have one right answer |
| semantic comparators | — | — | `quantized_interval`, `allclose_sign_invariant` | quantisation intervals and sign/phase-invariant factorisations; not value tolerances |

No tolerance was tuned per operator or per shape: every dropped combination
below is a stock-Triton compile failure or a numerical mismatch under this
single table, and the failure is recorded rather than patched.

**Scope:** the table applies only to the dtypes task 2 *added* to an operator. Every
dtype an operator already declared keeps its own case builder and its original,
tighter tolerances (`_ENRICH_ORIGINAL_DTYPES` in the enrichment wrapper routes
them to the original `make_case`), so enrichment never loosens an existing check.

#### held-out (26 operators)

The held-out list names held-out operators, so it is kept out of the
shipped corpus: `docs/history/heldout-cases.md` (maintenance branch only).

The recurring causes are:

1. **Triton math intrinsics are fp32/fp64-only on stock Triton 3.8** —
   `tl.exp`, `tl.log`, `tl.sqrt`, `tl.sin`, `tl.cos`, `tl.sigmoid`, `tl.erf`,
   `tl.floor`, etc. applied directly to a low-precision load. This accounts
   for most of the perf lane and a large part of the dev list. The kernel is
   untouched (this task only changes cases), so the operator keeps `float32`.
2. **The kernel casts or accumulates in a way that is numerically tied to a
   dtype** — e.g. `finalize_stats` (fp16 NaN sentinel), `nanmedian` (fp32
   `float_info.max` sentinel), SVD/QR/least-squares (factor signs/phase),
   eigendecompositions, `splitk_gemv` (bf16
   split-K cancellation). Those dtypes are dropped; the fp32 (or fp16) case
   remains.
3. **A new tail shape is not a legal case for that operator** — e.g.
   `softplus` derives `BLOCK_SIZE` from the shape (127 is not a power of two),
   `control_flow` keys its config map by shape, and several makora matmul
   cases hard-code `N=32768` with a fixed block layout. The added tail is
   removed; the original aligned shape remains.

All final cases were run on stock Triton 3.8 with `TRITON_F32_DEFAULT=ieee`,
one process per operator, `--allow-torch` (autotuner), GPUs 4 and 5:

|---|---:|---|

| pool = suite + held-out | 5612 | **5612 / 5612 PASS** |

Nothing was fixed by loosening a tolerance, editing a `ref`'s mathematics, or
deleting a passing case. The one `ref` change (`triangular_inverse_kernel`)
casts the inputs to float64 and casts the result back, exactly the
"compute the reference in fp64 from the low-precision inputs and cast"
pattern required by the task; it does not change the mathematical function.
The `det` change is case-layer data only and keeps the determinant finite.
The perf-lane workload verification (`harness/benchmark/run.py
--verify-only`, every (operator, dtype) entry at its steady-state size) was
completed after task 2 on GPU 5: of the 248 expanded entries, 239 PASS and are
the workload; the 9 below were dropped (§10.6).
